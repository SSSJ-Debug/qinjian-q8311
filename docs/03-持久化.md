# 03 · 持久化：让 ADB 每次开机自己回来

> 这一篇解决"每次重启都要重抓一次窗口"的痛点。
> **结论先行：`adb_enabled=1` 单靠写值不够，必须制造一次"变化事件"。**

---

## 一、先纠正一个普遍误解

很多教程说：`settings put global adb_enabled 1` 就永久打开了 USB 调试。

**这句话在这类设备上是错的。**

实测：

```
写入 adb_enabled=1  →  当场 USB 组合变回 9020，adb devices 出现设备   ✅
重启设备            →  adb_enabled 读出来仍然是 1
                    →  但 USB 组合退回 9002，adb 又没了                ❌
```

值一直在，就是不生效。

---

## 二、根因：一次竞态，不是权限问题

`UsbDeviceManager` 里有两套机制：

```java
// ① 开机初始化：读一次当前值，决定 USB 组合
boolean adbEnabled = Settings.Global.getInt(cr, ADB_ENABLED, 0) != 0;
setAdbEnabled(adbEnabled);

// ② 注册观察者：只在值"发生变化"时才重算组合
mAdbSettingsObserver = new AdbSettingsObserver();   // 监听 ADB_ENABLED
```

开机的时序：

```
t=0    UsbDeviceManager 构造，读 ADB_ENABLED
       → SettingsProvider 还没加载完
       → 拿到默认值 0
       → USB 组合 = 无 adb

t=2s   SettingsProvider 加载完成，ADB_ENABLED 实际是 1
       → 但广播已经错过了

t=3s   AdbSettingsObserver 注册
       → 从此开始监听"变化"
       → 可是值从 t=2s 起就是 1，之后没变过
       → observer 永远不触发
```

**所以 adb 就这样被永久摘掉了，直到下一次值发生变化。**

---

## 三、解法：主动制造一次变化

既然 observer 只在"变化"时触发，那就给它一个变化：

```bash
settings put global adb_enabled 0     # 先归零
sleep 1
settings put global adb_enabled 1     # 再置一 —— 这次 observer 一定听到
```

实测日志：

```
I/QJTOOLS: boot check start: usb.config=diag,serial_tty,serial_smd,adb  adb_enabled=1
I/QJTOOLS: boot fix: 写 0 → 等 1.2s → 写 1
I/QJTOOLS: boot fix done ok=true
I/UsbDeviceManager: setAdbEnabled(true) → functions 重算
→ USB 重新枚举成 9020，adb 自己回来了
```

**这个动作必须在系统完全启动之后做**（`BOOT_COMPLETED` 广播之后），
否则 AMS/SettingsProvider 还没就绪，写了也白写。

---

## 四、落地：一个开机自启的 App

最省事的载体是一个小 App，注册 `BOOT_COMPLETED` 广播：

```xml
<receiver android:name=".BootReceiver" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED"/>
    </intent-filter>
</receiver>
```

```java
public class BootReceiver extends BroadcastReceiver {
    @Override public void onReceive(Context ctx, Intent intent) {
        final PendingResult pr = goAsync();       // 别让广播提前结束
        new Thread(() -> {
            try {
                Thread.sleep(20_000);             // 等系统彻底起来
                for (int i = 0; i < 12; i++) {
                    String usb = getprop("sys.usb.config");
                    if (usb.contains("adb")) break;   // 已经有 adb，不打扰

                    set("adb_enabled", "0");
                    Thread.sleep(1200);
                    set("adb_enabled", "1");
                    Thread.sleep(1500);

                    if ("1".equals(get("adb_enabled"))
                            && getprop("sys.usb.config").contains("adb")) break;
                }
            } finally { pr.finish(); }
        }).start();
    }
}
```

### 三个关键细节

1. **等 20 秒再动手** —— 太早 AMS 没起来，写了不生效
2. **先检查 `sys.usb.config`** —— 已经有 adb 就跳过，别把用户正在用的通道打断
3. **最多重试 12 轮** —— 大约覆盖开机后 1 分钟的时间窗，足够

### 写 settings 需要权限

普通 App 写不了 `Settings.Global`，需要 `WRITE_SECURE_SETTINGS`。授予方式：

```bash
adb shell pm grant <包名> android.permission.WRITE_SECURE_SETTINGS
```

这个权限是 `signature|privileged|development`，shell 可以用 `pm grant` 授予（因为 shell 有 `GRANT_RUNTIME_PERMISSIONS`）。
一旦授予，**重启不丢**（记录在包管理器的运行时权限表里）。

## 五、还有一条更彻底的路：`persist.adb.tcp.port`

理论上如果能把 `persist.adb.tcp.port` 写进 `/data/property`，adbd 每次开机都会直接监听 5555，
连 USB 窗口都不需要了。

但实测在这类"属性白名单极严"的 ROM 上：

```
$ adb shell setprop persist.adb.tcp.port 5555
（静默失败，getprop 返回空）
```

`property_contexts` 里没有对应条目 → 被当作未定义属性 → SELinux 拒绝。

**如果你手上的设备能写进 `persist.adb.tcp.port`，优先用这条路**，它比 BootReceiver 更彻底：

```bash
adb shell setprop persist.adb.tcp.port 5555
adb shell getprop persist.adb.tcp.port       # 能读回 5555 才算成功
adb reboot
# 起来之后直接 adb connect <IP>:5555，不需要窗口
```

判断方法：看 `/property_contexts` 里有没有对应前缀的 allow 规则，
或者直接试 —— 能读回值就是能写。

---

## 六、验证持久化是否真的成了

不要只看"这次重启 adb 回来了"，要连续测三次：

```bash
for i in 1 2 3; do
    adb reboot
    sleep 60
    adb devices                       # 应该自动出现设备
    adb shell getprop sys.usb.config  # 应该含 adb
    adb shell settings get global adb_enabled   # 应该是 1
done
```

三次都过，才算真的焊死了。

## 七、如果 BootReceiver 不可行（没法装 App / 没权限）

退路还有：

| 退路 | 做法 | 局限 |
|---|---|---|
| 每次重启重抓 | 跑 `scripts/harvest.sh` | 人得守着开机 |
| 插着常供电的 USB | 让设备永不重启 | 治标 |
| 物理按键宏 | 用 USB 键盘/单片机模拟开机后操作 | 过度工程 |

现实一点说：**这类设备的常态就是"重启后要重抓一次"**。
把脚本固化成"插上就能跑"，比追求 100% 自动化更实际。
