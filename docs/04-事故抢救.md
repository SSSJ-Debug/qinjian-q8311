# 04 · 事故抢救：两条通道全断了怎么办

> 这篇是本项目最贵的一页。
> **我们真的把自己锁在门外过一次，靠这套流程救回来的。**

---

## 一、先看症状对不对

```
$ adb devices
（空）

$ ioreg / lsusb
设备在，PID = 9002    ← 无 adb 接口

$ ping <设备IP>
超时                   ← WiFi 也联系不上
```

**USB 无 adb + WiFi 不通 = 双通道归零。**
软意义上的"砖"：设备好好的在跑，但你一根手指都碰不到它。

---

## 二、先搞清楚"为什么会变成这样"

通常不是单一原因，而是一条链：

```
① 你做了某个会导致 system_server 崩溃的操作
        ↓
② system_server 崩 → 整机重启
        ↓
③ 重启清空内存属性 service.adb.tcp.port=5555
   （adbd 不再监听网络端口）
        ↓
④ UsbDeviceManager 读到 adb_enabled 的时机不对
   → USB 组合里没有 adb → 只剩 9002
        ↓
⑤ 而 WiFi 此时又是关的（或飞行模式开着）
        ↓
⑥ 双通道 = 0
```

第 ③④ 步是这类设备的物理特性，改不了；
**但第 ① 步是人为的，这才是真正该防的。**

### 什么操作会导致 ①

| 危险操作 | 为什么会崩 |
|---|---|
| 反复 `am start` 一个 layout 缺失的 Activity | 每次崩一次进程，连续崩会触发 AMS 的 WTF 级保护，把 system_server 拖下水 |
| `am force-stop` 关键系统服务 | 有的服务被杀后没有兜底，连带拖垮 system_server |
| 大范围 `settings put` | 部分 ROM 的 observer 链有 bug，会死循环 |
| `pm disable` 核心组件 | 启动链断裂，开机直接卡死 |

**红线：任何"故意让它崩"的调试手法，在单通道状态下都是自杀。**

---

## 三、抢救流程（照抄）

### 步骤 0：先确认是不是真的全断了

有时候只是 adb server 挂了：

```bash
adb kill-server
adb start-server
adb devices
```

别急着拔线。

### 步骤 1：准备一个"会自己等"的脚本

关键认知：**你抢到的那个窗口只有 8 秒，来不及做复杂操作。**
所以不要试图在窗口内完成所有事，而是**塞一个脚本进去让它自己干**。

```bash
# 先启动蹲守（这个脚本会一直跑）
./scripts/revive.sh
```

然后：

### 步骤 2：制造一个窗口

```bash
# 拔掉 USB
# 等 10 秒（确认完全断电）
# 插回去
```

如果是带电设备（有电池），拔 USB 不一定重启，需要**长按电源键强制重启**。

### 步骤 3：窗口内只做三件事

```bash
1. push agent.sh  → 把脚本送进去
2. chmod +x       → 给执行权限
3. setsid 启动    → 让它脱离 adb 会话
```

**不要**在窗口内 `pm install`、不要 `settings put`（会崩）、不要 `adb pull`（太慢）。

### 步骤 4：让设备侧脚本自己完成剩下的

它会在设备内部等到 AMS 就绪，然后：

```
关飞行模式 → 开 WiFi → 制造 adb_enabled 的 0→1 变化 → adb 回到 USB 组合
```

**这一步之后，USB 通道会自己回来**（不用再插拔）：

```
$ ioreg / lsusb
PID = 9020   ← adb 回来了

$ adb devices
<序列号>  device   ← 通道恢复
```

### 步骤 5：WiFi 通道也一起救

设备侧脚本已经执行了 `svc wifi enable`，等十几秒：

```bash
adb connect <设备IP>:5555
adb devices
# 应该同时看到 USB 和 IP 两个设备
```

## 四、为什么"设备侧脚本"能成功而"宿主机直接下命令"不行

| 方式 | 卡在哪 |
|---|---|
| 宿主机在窗口内直接 `settings put` | AMS 没起来 → 报 `IActivityManager == null`；等 AMS 起来窗口已关 |
| 宿主机在窗口内 `svc wifi enable` | shell 没有 `CHANGE_WIFI_STATE` → 直接抛 `SecurityException` 把命令自己搞崩 |
| **设备侧脚本** | 脚本在设备内部跑，**没有 adb 的超时限制**，可以慢慢重试到成功 |

最后一条是关键：**adb shell 单条命令的存活时间受会话约束，脚本不受。**

## 五、防复发：三条必须遵守的纪律

### 纪律 1：动手前先数通道

```bash
adb devices
# 只有一行  → 单通道，禁止做任何可能触发重启的操作
# 有两行    → 双通道，可以冒险
```

单通道时，**第一优先级是把第二条通道补回来**，而不是继续做你的实验。

### 纪律 2：任何开关操作后必须回读

```bash
settings put global airplane_mode_on 0
settings get global airplane_mode_on    # ← 必须验证，不能只看命令有没有报错
```

**看 UI 不算，读属性才算。** 有的 ROM 上开关是"坏"的（点了没视觉反馈），
但属性其实变了，或者反过来。不读永远不知道真实状态。

### 纪律 3：不要用"崩溃"当重启手段

需要重启某个服务时，用可预期的方式：

```bash
# 不要这样
am start -a android.settings.APN_SETTINGS   # layout 缺失必崩，会连坐 system_server

# 要这样
svc data disable && svc data enable
# 或者干脆整机重启（重启是可预期的，崩溃不是）
```

## 六、如果抢救失败

按概率排序的后续手段：

| 手段 | 成功率 | 代价 |
|---|---|---|
| 换一根确定能传数据的 USB 线 | 中 | 一根线 |
| 换一个 USB 口 / 换一台电脑 | 中 | 时间 |
| 冷启动（拔电池 / 断电 30 秒）再蹲窗口 | 高 | 时间 |
| 拆机短接进入 EDL（9008） | 高 | 需要 firehose 包，风险大 |
| 找厂商售后 | 100% | 钱 |

> **在放弃之前，一定是先确认"线"和"口"没问题。**
> 我们见过太多次：折腾三小时，最后是线只有供电没有数据。

---

## 七、一句话总结

> **设备不会无缘无故失联，都是某一步操作导致的。
> 抢救的核心不是"更快地抢窗口"，而是"让设备自己把自己救回来"。**
