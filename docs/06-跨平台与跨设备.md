# 06 · 跨平台与跨设备

> 方法是通用的，但每个平台、每类设备都有自己的小脾气。

---

## 一、三个平台的差异

| 项目 | macOS | Linux | Windows |
|---|---|---|---|
| USB 枚举查看 | `ioreg -p IOUSB -w0 -l` | `lsusb` / `dmesg` | 设备管理器 / `Get-PnpDevice` |
| 驱动 | 免装，adb 原生走 USB | 需 udev 规则或 sudo | **需手动装 ADB 驱动** |
| 串口干扰 | 无 | `qcserial` / `option` 会抢串口接口 | 需装 QDLoader 之类 |
| 脚本 | bash | bash | PowerShell |
| 轮询精度 | 好 | 好 | `Start-Sleep -Milliseconds` 精度略差 |

### macOS

```bash
# 看 USB（找 idProduct：36866=0x9002 无 adb，36896=0x9020 有 adb）
ioreg -p IOUSB -w0 -l | grep -A12 "Android"
```

零门槛。`adb` 直接就能看到设备，不需要任何驱动。

### Linux

```bash
lsusb | grep 05c6
dmesg | grep -iE "qcserial|option|usb 1-"

# udev 规则（避免每次 sudo）
echo 'SUBSYSTEM=="usb", ATTR{idVendor}=="05c6", MODE="0666"' | sudo tee /etc/udev/rules.d/51-android.rules
sudo udevadm control --reload-rules && sudo udevadm trigger
```

**注意**：`qcserial` / `option` 驱动会绑定到高通的串口接口（interface 0/1），
这**不影响** ADB 接口（interface ff/42/01）。看到 `/dev/ttyUSB0` 反而是好事——说明设备确实在。

### Windows

```powershell
Get-PnpDevice | Where-Object {$_.InstanceId -like "*VID_05C6*"}
```

必须先装驱动，否则设备在设备管理器里是个带感叹号的"未知设备"：

1. 设备管理器 → 找到 `VID_05C6` 那个 → 更新驱动程序
2. 浏览计算机 → 让我从列表中选取 → Android Device → Android ADB Interface
3. 没有这一项就装 Google USB Driver（Android SDK 里）

装好之后 `adb devices` 才能看到。

## 二、高通以外的平台

| 平台 | 能不能用这套 | 说明 |
|---|---|---|
| **高通（05c6）** | ✅ 主力场景 | diag/serial/adb 动态组合，就是这个方法诞生的地方 |
| **联发科（0e8d）** | ⚠️ 部分可用 | MTK 的 USB 组合逻辑不同，但同样有 `adb_enabled` 机制；`preloader` / `bootrom` 模式另算 |
| **展讯（1782）** | ⚠️ 未知 | 需要实测 |
| **瑞芯微（2207）** | ⚠️ 类同 | 常用 `rkdeveloptool`，ADB 通常直接可用 |
| **Amlogic（1b8e）** | ✅ 通常有 adb | 电视盒子常直接带 ADB，不需要窗口收割 |

**通用判据**：只要满足下面两条，这套方法就有戏 ——

1. 开机过程中 USB PID 会变（说明组合是动态的）
2. `persist.sys.usb.config` 里含 `adb`

```bash
# 窗口期内执行
adb shell getprop persist.sys.usb.config
adb shell getprop ro.adb.secure
```

如果 `ro.adb.secure=1`，难度会显著上升（见下）。

## 三、`ro.adb.secure = 1` 的设备怎么办

这种情况下，连上去之后设备会弹一个"允许 USB 调试吗"的对话框，**必须点允许**。

问题：对话框要等系统起完才弹，而那时窗口已经关了。

可用的思路：

| 思路 | 可行性 |
|---|---|
| 窗口期内盲点屏幕 | 极难，要精确知道对话框位置和出现时机 |
| 提前塞 `adb_keys` | 需要 root 或可写 `/data/misc/adb` |
| 用 `input keyevent` 盲操作 | 部分 ROM 可行（KEYCODE_DPAD_CENTER 确认） |
| 找厂商的授权白名单接口 | 罕见 |

**现实建议**：如果是 `ro.adb.secure=1` 且屏幕不可操作，这套方法的成功率会很低，
不如考虑拆机走 UART / EDL 路线。

## 四、设备形态带来的额外问题

### 圆形屏 / 小屏设备

- 截图是旋转过的，`input tap` 要换算坐标（见 [05-踩坑 #8](05-踩坑清单.md)）
- 矩形对话框的四角会被裁掉，**「始终」按钮可能落在圆外点不到**
- 软键盘会挡住下半屏，用 `input keyevent 4` 先收键盘

### 无触摸屏设备（纯语音音箱）

只能靠 ADB 操作，`input` 系列全废。所有 UI 交互都得走 `am start` / `settings put` / 广播。

### 有电池的设备

"拔电源"不等于断电。要真正冷启动得长按电源键，或者等电池耗尽。

## 五、跨设备通用的自检清单

拿到一台新机器，按这个顺序查：

```bash
# 1. 有没有 USB 反应
#    macOS: ioreg -p IOUSB | grep -A5 05c6
#    Linux: lsusb | grep 05c6

# 2. 窗口期内（开机那几秒）能拿到什么
adb shell getprop ro.adb.secure          # 0 = 有戏
adb shell getprop persist.sys.usb.config # 含 adb = 有戏
adb shell getprop ro.product.model
adb shell getprop ro.build.version.release
adb shell id                              # 看是什么身份

# 3. 能不能写属性（决定能不能持久化）
adb shell setprop persist.adb.tcp.port 5555
adb shell getprop persist.adb.tcp.port    # 能读回 = 能持久化

# 4. 有没有 root
for p in /sbin/su /system/bin/su /system/xbin/su /su/bin/su; do [ -x "$p" ] && echo "$p"; done
adb shell getenforce                      # Enforcing 且无 su 域 = 提权基本没戏
```

四条查完，这设备能不能搞就有结论了。
