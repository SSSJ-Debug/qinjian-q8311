# 01 · 原理：ADB 为什么只存在几秒

> 这一篇讲清楚"为什么 `adb devices` 是空的，但设备其实有 ADB"。
> 想通了这一层，后面所有操作都顺理成章。

---

## 一、USB 组合是动态的

高通平台（以及很多定制 ROM）用一套叫 **USB Composition** 的机制，把多个功能接口打包成不同的"组合"，
同一个设备在不同阶段枚举成不同的 PID：

| VID:PID | 组合内容 | 有 ADB |
|---|---|---|
| `05c6:9002` | `diag,serial_tty,serial_smd` | ❌ |
| `05c6:9020` | `diag,serial_tty,serial_smd,adb` | ✅ |
| `05c6:9008` | EDL（紧急下载） | — |

组合由系统属性控制：

```
sys.usb.config          ← 当前组合（运行时）
persist.sys.usb.config  ← 开机默认组合（持久化）
```

以及一个设置项：`Settings.Global.ADB_ENABLED`。

---

## 二、开机时到底发生了什么

```
 0s   内核启动，USB 枚举成 9002（无 adb）
  ↓
 3s   init 启动 adbd（因为 persist.sys.usb.config 里有 adb）
      → USB 重新枚举成 9020  ← 窗口开始
  ↓
 8s   system_server 起来，UsbDeviceManager 初始化
      → 读 Settings.Global.ADB_ENABLED
  ↓
10s   读到 0（出厂默认）
      → setAdbEnabled(false)
      → USB 组合重算成 "diag,serial_tty,serial_smd"
      → 摘掉 adb 接口  ← 窗口结束
  ↓
14s  USB 退回 9002，adb devices 变空
```

**窗口 = 3s ~ 10s，实测 8~14 秒，不稳定。**

影响因素：adbd 启动速度、系统启动负载、USB 重新枚举的时机、是否有开机动画拖时间。

---

## 三、为什么"打开 USB 调试开关"也救不了

很多人会想：那我去设置里把 USB 调试打开不就行了？

问题在于**时序**：

```java
// UsbDeviceManager 里有两个东西
1. 开机初始化时：读一次 ADB_ENABLED，决定 USB 组合
2. AdbSettingsObserver：监听 ADB_ENABLED 的"变化事件"，值变了才重算组合
```

如果开机时读到 `0`，adb 被摘掉。
之后你在设置里打开开关，值变成 `1` —— 但**如果 observer 还没注册**（`SettingsProvider` 加载晚于 USB 初始化），
这次变化就没人听到，adb 永远回不来。

**这是一个竞态，不是逻辑错误。** 厂商的 ROM 里这个竞态几乎必然发生。

所以你会看到这种诡异现象：

```
adb_enabled = 1        ← 开关明明是开的
sys.usb.config = diag,serial_tty,serial_smd   ← 但组合里就是没有 adb
```

---

## 四、关键推论：先切 TCP，再慢慢来

窗口期有个致命限制：

```
窗口期（0~10s）：ActivityManager 还没发布
                 → settings put 会抛 IActivityManager == null
                 → am / pm 全不能用
                 → 只有 setprop 能用（init 属性服务比 AMS 早得多）

系统起完（10s+）：settings 能用了
                 → 但 adb 已经没了
```

**死循环。**

唯一的破法：在窗口期内做一件事，让 **adbd 换一个地方监听** —— 网络。

```bash
adb tcpip 5555
# 内部等价于 setprop service.adb.tcp.port 5555 + 重启 adbd
```

之后 adbd 在 `5555` 端口上监听，**不再依赖 USB 组合**。
哪怕 USB 已经退回 9002，网络侧依然是活的。

这就是整个方法的支点。

---

## 五、`service.adb.tcp.port` 是内存属性

必须记住这条：

| 属性 | 是否跨重启 |
|---|---|
| `persist.sys.usb.config` | ✅ 持久（在 /data/property） |
| `service.adb.tcp.port` | ❌ **内存属性，重启清零** |
| `settings global adb_enabled` | ✅ 持久（在 settings 数据库） |

所以：

- `adb tcpip 5555` 只在**这次开机**内有效
- 重启后 5555 端口没了，USB 又是 9002 → **两条通道同时失联**
- 想跨重启保住通道，必须靠设备侧有个东西在开机后重新焊一次（见 [03-持久化](03-持久化.md)）

---

## 六、一个容易忽略的前提：`ro.adb.secure`

```
ro.adb.secure = 0   → 不需要在屏幕上点"允许 USB 调试"，谁连都放行
ro.adb.secure = 1   → 必须在窗口期内完成授权点击
```

**大部分白牌机/定制机是 0**（产线测试图省事），这让我们能在几秒内完成操作。

如果是 `1`，难度会高一个数量级：
窗口期只有 8 秒，而授权对话框要等系统起完才弹 —— 你根本没时间点。
那种情况需要另一套思路（比如提前在 `/data/misc/adb/adb_keys` 里塞公钥，但那又要 root）。

先查这个值，它决定了这件事的难度档位：

```bash
# 窗口期内执行
adb shell getprop ro.adb.secure
adb shell getprop persist.sys.usb.config
```

---

## 小结

| 结论 | 意义 |
|---|---|
| ADB 只在开机前 10 秒存在 | 所以策略是"蹲守"而不是"连接" |
| 窗口期只能用 `setprop` | 所以别在窗口期写 settings，会白费窗口 |
| `adb tcpip` 能摆脱 USB 组合 | 这是唯一的破局点 |
| `service.adb.tcp.port` 不持久 | 所以每次重启都要重来，或者做开机自修复 |
