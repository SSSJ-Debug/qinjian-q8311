# 05 · 踩坑清单

> 按"踩到的概率"排序。前 5 条几乎人人都会踩。

---

## 1. 误判"这台机器没有 ADB"

**现象**：`adb devices` 空，USB 显示 `05c6:9002`。

**真相**：USB 组合是动态的，ADB 只在开机瞬间存在 8~14 秒。

**解法**：蹲守，不要直接连。见 [01-原理](01-原理.md)。

---

## 2. 窗口期写 `settings` 必崩

**现象**：
```
Exception occurred while executing:
java.lang.NullPointerException: ... IActivityManager ... on a null object reference
```
或 `SecurityException: Permission Denial`。

**真相**：ActivityManager 还没发布。窗口期的 `settings` 命令依赖 `system_server`。

**解法**：窗口期只用 `setprop`；要写 settings 就等网络侧接管，或者用设备侧脚本。

> 很多人以为是权限不够，跑去折腾 SELinux —— 方向完全错了。

---

## 3. 以为 `adb tcpip` 执行失败（其实成功了）

**现象**：
```
$ adb tcpip 5555
restarting in TCP mode port: 5555
$ adb devices
（空）
```

**真相**：`tcpip` 会重启 adbd，USB 连接必然断开。这是预期行为。

**解法**：立刻转网络侧 `adb connect <IP>:5555`。别在原地重试。

---

## 4. 高频轮询把宿主机拖卡

**现象**：抓窗口时电脑风扇狂转，卡到不能动。事后一查，堆了 5 万个 `adb` 进程。

**真相**：0.05~0.1 秒的轮询间隔，每次 fork 两个进程，40 分钟就能积累到这个量级。

**解法**：间隔 0.3~0.5 秒，并且给脚本设总时长上限（比如 30 分钟自动退出）。

---

## 5. `adb pull` 拉下来的 APK 装不上

**现象**：拿到的 APK `Failure [INSTALL_FAILED_INVALID_APK]`。

**真相**：用了 `adb shell cat /system/app/xxx.apk > local.apk`。
shell 的 stdout 会对二进制做处理（换行转换 / 截断），文件被破坏。

**解法**：永远用 `adb pull`，它走的是二进制安全通道。

---

## 6. `pm disable` 被拒，以为没有权限

**现象**：
```
SecurityException: Neither user 2000 nor current process has
android.permission.MANAGE_USERS
```

**真相**：shell uid 确实没有 `MANAGE_USERS`。

**解法**：改用 `pm hide`。它是"对当前用户隐藏"，不需要系统权限，效果对普通使用场景足够。

```bash
pm hide com.example.setupwizard     # ✅
pm disable com.example.setupwizard  # ❌ 权限不够
```

---

## 7. `pm hide` 了激活向导，开机还是弹

**真相**：还差两个标记位。

**解法**：
```bash
settings put global device_provisioned 1
settings put secure user_setup_complete 1
```

---

## 8. `input tap` 点偏

**现象**：截图里明明看到按钮，点下去没反应。

**真相**：屏幕 rotation=1 时，**截图是旋转过的**，物理坐标和逻辑坐标差一个 90°。

**解法**（rotation=1，物理 768×1024，逻辑 1024×768）：

```
截图坐标 (x, y)  →  tap 坐标 (y, 768 - x)
```

用一次就记住了。或者干脆改用 `input keyevent` 做方向导航，避开坐标问题。

---

## 9. 前台被原厂 App 抢走

**现象**：刚 `am start` 自己的界面，两秒后被打回原厂时钟/相机。

**真相**：原厂 App 有前台服务或定时器，会周期性把 Activity 拉到前台。

**解法**：逐个 `am force-stop`。但要小心 —— 杀系统关键进程可能导致重启（见 [04](04-事故抢救.md)）。

---

## 10. 重启后一切白干

**现象**：`adb_enabled=1` 写进去了，重启又没了。

**真相**：`service.adb.tcp.port` 是内存属性；`adb_enabled` 虽然持久，但存在竞态（见 [03](03-持久化.md)）。

**解法**：BootReceiver 制造变化事件，或者接受"每次重启重抓一次"。

---

## 11. `uiautomator dump` 返回空根节点

**现象**：
```
ERROR: null root node returned by UiTestAutomationBridge.
```

**真相**：部分定制 ROM 裁掉了 Accessibility 相关组件，或者 `UiAutomation` 服务被禁用。
另外这个命令在某些 ROM 上还会**把 system_server 搞崩**。

**解法**：不要依赖 uiautomator。用 `screencap` 截图 + 坐标换算，或者直接在 App 里加日志。

---

## 12. `adb shell` 里没有 `head` / `tail` / `grep` 的部分功能

**现象**：
```
/system/bin/sh: head: not found
```

**真相**：Android 5.x 的 toolbox 工具极其简陋，`head`/`tail`/`awk` 可能都没有。

**解法**：把过滤放到宿主机侧做：

```bash
adb shell "dumpsys activity" | grep mResumedActivity   # ✅ 宿主机过滤
adb shell "dumpsys activity | grep mResumedActivity"   # ❌ 设备上没有 grep 就崩
```

---

## 13. `setprop` 静默失败

**现象**：
```bash
$ adb shell setprop persist.adb.tcp.port 5555
$ adb shell getprop persist.adb.tcp.port
（空）
```
没有报错，但也没生效。

**真相**：属性不在 `property_contexts` 白名单里，或者 shell 域没有 set 权限。
SELinux 拒绝时，`setprop` 通常不会返回错误码。

**解法**：
1. 查 `/property_contexts` 有没有对应前缀
2. 每次 `setprop` 后**必须 `getprop` 回读**
3. 如果确认写不进，接受现实，换方案（BootReceiver / 网络侧）

---

## 14. 以为"没有 root 就什么都做不了"

**真相**：ADB 通道本身提供的权限已经很大了：

| 能做 | 不能做 |
|---|---|
| 装/卸应用、`pm hide` | 改 `/system` |
| `settings put`（大部分 key） | 读写其他应用私有目录 |
| `am`/`input`/`screencap` | 改内核参数 |
| 读写 `/sdcard`、`/data/local/tmp` | 提权到 uid 0 |

**很多"需要 root"的教程，其实 ADB shell 就能做。** 先试，别预设做不到。

---

## 15. 忘记 `adb kill-server` 导致设备被抢

**现象**：某个工具（IDE、手机助手、WebUSB 页面）连上了设备，你的 `adb` 就看不到它了。

**真相**：adb 是独占的，一个设备只能被一个 adb server 管理。
WebUSB 类工具（很多网页版搞机工具）会直接抢 USB 设备。

**解法**：
```bash
adb kill-server      # 让给别的工具
# ...用别的工具...
adb start-server     # 抢回来
```

---

## 16. 用 `su` 判断有没有 root —— 结论容易反

**现象**：`su: not found`，于是认为"没有 root"。

**真相**：`su` 不在 `$PATH` 里不代表没有。
有的 ROM 把 su 放在 `/sbin/su`、`/system/xbin/su`、`/su/bin/su`。

**解法**：全路径都试一遍：

```bash
for p in /sbin/su /system/bin/su /system/xbin/su /su/bin/su /magisk/.core/bin/su; do
    [ -x "$p" ] && echo "found: $p"
done
```

但注意：**SELinux 是 Enforcing 且 sepolicy 里没有 su 域的话，就算有 su 二进制也提不了权。**

---

## 一条元经验

> **所有"看起来没反应"的现象，先怀疑自己的前提假设，再怀疑设备。**
>
> 我们花时间最多的不是操作，是"以为 ADB 不存在"、"以为 tcpip 失败了"、
> "以为 settings 是权限问题"——三个错误前提，各浪费了半天到两天。
