# 02 · 窗口收割：把这几秒稳稳抓住

> 核心就一句：**脚本要在开机之前就跑起来，并且轮询得足够快。**

---

## 一、轮询间隔怎么定

| 间隔 | 结果 |
|---|---|
| 0.05s | 宿主机 fork 爆炸（40 分钟能攒 5 万个进程，风扇狂转） |
| 0.1s | 仍然太猛，实测会把宿主机拖卡 |
| **0.3 ~ 0.5s** | **甜点区**，既抓得住 8 秒窗口，又不拖垮机器 |
| 1s | 窗口 8 秒只轮询 8 次，容易漏 |

如果窗口特别短（3~5 秒），可以降到 0.2s，但记得限制总时长。

---

## 二、脚本骨架

```bash
ADB=adb
while :; do
    # 只要 USB 设备：序列号里不含冒号
    S=$($ADB devices | awk 'NR>1 && NF>=2 && $1 !~ /:/ && $2=="device"{print $1; exit}')
    if [ -z "$S" ]; then sleep 0.4; continue; fi

    # 抓到了，立刻按价值排序执行
    ...
done
```

**过滤条件 `$1 !~ /:/`** 很重要：如果你已经连了 WiFi 设备（`192.168.1.5:5555`），
不加过滤会误把它当成"窗口抓到了"，然后对着一个已经正常的设备重复焊接。

## 三、按价值排序，随时被打断也不亏

窗口随时可能关闭，所以要**把最要紧的放最前面**：

```
1. settings put global adb_enabled 1     ← 保住 USB 通道（最重要）
2. adb tcpip 5555                        ← 多一条网络通道
3. settings put global airplane_mode_on 0  ← 别让飞行模式坑你
4. svc wifi enable                       ← 第二条通道上保险
5. device_provisioned / user_setup_complete ← 绕过激活向导（可选）
```

反例：把 `pm install` 放第一位 —— 装一个 3MB 的 APK 就要几秒，窗口直接结束，什么都没干成。

## 四、焊接为什么要循环 30 次

窗口期 `settings put` 会失败，报错长这样：

```
Exception occurred while executing:
java.lang.NullPointerException: Attempt to invoke interface method
'...IActivityManager...' on a null object reference
```

或者：

```
SecurityException: Permission Denial ...
```

这不是权限问题，是 **AMS 还没发布**。

但 AMS 发布的时刻和窗口关闭的时刻很接近（都在 8~14 秒内），
所以策略是**疯狂重试**：每 0.4 秒一次，一直试到成功或者窗口关闭。

实测中，有时第 1 次就成，有时要第 12 次才成 —— 取决于设备启动速度。

```bash
for k in $(seq 1 30); do
    adb -s "$S" shell settings put global adb_enabled 1 >/dev/null 2>&1
    V=$(adb -s "$S" shell settings get global adb_enabled 2>/dev/null | tr -d '\r ')
    [ "$V" = "1" ] && break
    sleep 0.4
done
```

**注意一定要 `get` 回读验证**，不能只看命令有没有报错 —— 窗口期命令经常"看起来执行了但没生效"。

## 五、`adb tcpip` 会主动断掉 USB，这是正常的

```
$ adb -s <serial> tcpip 5555
restarting in TCP mode port: 5555
$ adb devices
（空）              ← 别慌，这是预期行为
```

原理：`tcpip` 会重启 adbd 进程，USB 连接必然断开。
断开后 adbd 在 5555 端口等着，你需要从网络侧连回去。

**很多人在这里以为失败了就放弃了。** 记住这句话：`tcpip` 之后 USB 必定掉线。

## 六、设备侧常驻代理：绕过"窗口期写不了 settings"

如果 `adb tcpip` 因为网络原因不可用（比如 WiFi 是关的、拿不到 IP），
还有另一条路：**把脚本推进设备，让它在设备侧等**。

```bash
# 窗口内（只需要一条命令的空间）
adb -s "$S" push agent.sh /data/local/tmp/agent.sh
adb -s "$S" shell chmod 755 /data/local/tmp/agent.sh
adb -s "$S" shell "setsid /data/local/tmp/agent.sh </dev/null >/dev/null 2>&1 &"
```

`setsid` 让脚本脱离当前 adb 会话，**adb 断开后它还在跑**。

然后脚本自己等 AMS 就绪，再执行 `settings put` —— 这时候 adb 通道可能已经没了，
但没关系，脚本在设备内部执行，不需要 adb。

> 这是本项目里"救回设备"的关键一招。完整脚本见 [`scripts/agent.sh`](../scripts/agent.sh)。

### 三种脱离方式都试一遍

不同 ROM 对后台进程的处理不一样，`setsid` 不一定有：

```bash
adb shell "setsid /data/local/tmp/agent.sh </dev/null >/dev/null 2>&1 &"   # 首选
adb shell "nohup  /data/local/tmp/agent.sh </dev/null >/dev/null 2>&1 &"   # 备选
adb shell "sh     /data/local/tmp/agent.sh </dev/null >/dev/null 2>&1 &"   # 兜底
```

三条都发，哪条活下来算哪条。副作用最多是多跑几个实例，脚本内部有幂等保护就行。

## 七、用 `/proc` 判断进程是否活着，别信 `ps`

Android 上 `ps` 默认只显示 15 个字符的进程名，长名字会被截断，看起来像"进程没了"。

可靠做法：

```bash
# 精确判断某个脚本是否在跑
for p in /proc/[0-9]*; do
    if tr '\0' ' ' < "$p/cmdline" 2>/dev/null | grep -q "agent.sh"; then
        echo "活着: $p"
    fi
done
```

## 八、检查清单

抓窗口前，确认这几件事：

- [ ] `adb start-server` 已经跑过（避免第一次轮询被 server 启动耗时吞掉）
- [ ] 脚本在**开机之前**就已经在跑（先启动脚本，再上电/按电源键）
- [ ] 轮询间隔 0.3~0.5s
- [ ] 设备是数据线（很多 Micro-USB 线只有供电，没有数据）
- [ ] 驱动装好了（Windows 尤其容易漏）
- [ ] 日志开着，能看到每次轮询的中间状态
